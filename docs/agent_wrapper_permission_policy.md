# agent_wrapper 許可設計ポリシー

作成: 2026-07-10
参照元: 「コーディングエージェントにおける許可設計」(ユーザー提供の一般論)を本プロジェクト用に翻案したもの。
関連: tasks/alignment.md(用語定義)、docs/agent_wrapper_sdk_integration_plan.md(実装アーキテクチャ)

## 1. 目的 — 許可の逆説への対処

承認要求が細かすぎると、人間は内容を読まずに反射的に承認するようになり、
Human-in-the-loopは形骸化する。安全性は「承認の回数」ではなく
「人間が本当に判断すべき場面だけを、判断できる材料つきで届けること」で決まる。

2026-07-10の実運用でこの逆説を実際に観測した:

- claude実行(Box3D実装): ollama自動承認47件・人間承認12件・却下0件。人間承認12件の中には
  「main.jsの編集」「検証スクリプトの編集」など、計画の内部操作にすぎないものが多数含まれた
- codex実行(ダッシュボードUX改善): ファイル書き込みのたびにエスカレーションされ、
  ユーザーから「書き込みは普通OKな作業では」との指摘を受けた
- 「rm -rf検知テストの書き込み」が実削除と同じ見出しでエスカレーションされ、
  重要な承認とそうでない承認の区別がつかなかった(誤検知の可能性表示のTODOで対応)

## 2. このプロジェクト固有の前提(一般論との差分)

1. **人間は画面の前にいない**(作業をPCの外に出すことが目的。承認はスマホから行う)。
   承認1回のコストが通常の開発より高く、「意味のある単位でまとめる」重要性は一般論より増す。
2. **このゲートが唯一の安全装置**。一般論の「作業ブランチ内なら編集自由」は人間が後で
   diffを見る前提だが、ここでは「git管理下で取り消し可能」という条件の確認までゲート側の
   責務になる。自動化の条件は一般論より厳格に定義する。
3. **ollamaという中間層がある**。一般論のレベル分けを「rules(正規表現=確実に捕まえる網)」
   「ollama(内容を評価する一次受付)」「人間(最終判断)」の3層への割り当てとして実装する。

## 3. 変えない原則(tasks/alignment.md より)

- 破壊的操作への対応: AIが自動でdeny/approveせず、必ず人間に判断を委ねる
- 一次受付: ollamaは内容を評価して判断する(機械的な相槌は禁止)
- dangerously系フラグは使わない(エージェント側の権限確認機構を無効化しない)
- 判断がつかない場合は常に安全側(人間へのエスカレーション)に倒す

## 4. 許可レベル

### L0: 自動実行(読み取り)

影響がなく読み取りのみの操作。ollama一次判定でALLOWを既定とする。

- ファイル閲覧、コード検索、ディレクトリ一覧
- git status / git diff / git log の確認
- ログ・設定値・依存関係の確認
- テスト結果の読み取り

条件: 外部へのデータ送信を伴わないこと(curlで外部にPOST等はL0ではない)。

### L1: 計画内自動実行(ローカルで取り消し可能な変更)

git管理下の作業ディレクトリに閉じ、差分破棄で元に戻せる操作。
ollama一次判定でALLOWを既定とする。**「ファイルを書き込むから」という理由だけで
エスカレーションしない。**

- 作業ディレクトリ(cwd)配下・git管理下のファイル編集・新規作成
- テストコードの作成、テスト実行、lint、型チェック、フォーマット、ビルド
- ローカルサーバーの起動、差分の生成、ドキュメント更新
- 一時ディレクトリでの試作・検証スクリプト実行

ALLOWの条件(ollamaプロンプトに明記する):
- 変更先が cwd 配下であること(cwd外・ユーザープロファイル・システム領域への書き込みはL2以上)
- シークレットらしきファイル(.env、*credential*、*secret*、鍵ファイル等)でないこと
- 書き込み内容に外部送信・自動実行の仕掛け(スケジューラ登録等)を含まないこと

### L2: 計画承認が必要(設計・構造・外部への影響)

実行前に人間の承認を必要とする。rulesまたはollamaのESCALATEで人間に届ける。

- 依存パッケージの追加・更新(npm/pip/uv/cargo等。rules.pyで問答無用エスカレーション — 維持)
- git clone / docker pull / docker run 等の外部コード取得(同上 — 維持)
- 公開API・データモデル・DBスキーマの変更
- 認証・認可・暗号化処理の変更
- 設定ファイル構造の変更、外部API連携の追加
- 後方互換性を壊す変更、大規模リファクタリング
- cwd外への書き込み

承認要求には「目的・方針・変更範囲・影響・リスク・戻し方」を含める
(現状はollama explain_operationの説明がこれに相当。将来は計画承認フローで束ねる)。

### L3: 実行直前の明示的承認が必要(対外的・破壊的・非可逆)

計画が承認済みでも、実行直前に必ず人間の承認を取る。rules.pyの問答無用パターンで捕まえる。

- rm -rf 等の再帰削除、git reset --hard、git履歴書き換え、force push(実装済み)
- main/releaseへのpush・マージ、リモートブランチ削除(**パターン追加が必要**)
- 本番デプロイ、本番設定変更、本番DB操作(**パターン追加が必要**: deploy/publish/release系)
- シークレット・APIキーの変更、外部サービスへの実データ送信
- パッケージ・コンテナイメージの公開、課金リソースの作成

理由: コードはgitで戻せても、送信済みデータ・公開済みパッケージ・削除済みデータ・
発生した課金は取り消せない。

## 5. 実装へのマッピング

| レベル | 主担当 | 実装先 | 状態 |
|---|---|---|---|
| L0 | ollama | judge_permission のALLOW基準をプロンプトに明記 | 未実装(現状も概ねALLOWだが基準が暗黙) |
| L1 | ollama | 同上。「git管理下・cwd配下の編集はALLOW」を明記 | **未実装(今日の主課題)** |
| L2 | rules + ollama | インストール系はrules(実装済み)。その他はollamaのESCALATE基準に明記 | 一部実装 |
| L3 | rules | DESTRUCTIVE_PATTERNSにデプロイ・公開・main反映系を追加 | 一部実装 |

補足:
- ollamaの判定に迷いがある場合のフェイルセーフ(ESCALATE)は全レベルで維持する。
- L1の「git管理下か」の確認は、ollamaの推測に頼らずラッパー側で機械的に判定して
  ollamaへのプロンプトに事実として渡す方が確実(将来実装の設計メモ)。

## 6. 実装計画単位の承認フロー(実装済み)

一般論の中核「許可は実装計画単位で求める」の翻案:

1. セッション開始時、エージェントに実装計画(目的・方針・変更範囲・依存・影響・リスク・
   戻し方・検証方法)の提示を義務付ける(ラッパーが初期プロンプトに指示を差し込む)
2. 計画はダッシュボードに常設表示され、人間が1回承認する
3. 承認後、ollamaの一次判定に「承認済み計画の範囲内か」という基準が加わる:
   範囲内のL0/L1操作→ALLOW、範囲外・L2/L3→人間へ
4. 再承認が必要になる条件: 変更対象の大幅な拡大、新しい依存、互換性破壊、
   セキュリティ判断、外部送信、当初の復旧方法が使えなくなる場合

実装では最初の応答全文を計画として扱い、却下・説明要求後の次の応答全文を改訂計画として
再承認にかける。計画ターンも既存の会話上限に含め、上限到達時は既存どおり人間へ
継続可否をエスカレーションする。対象はClaudeRunner/CodexRunnerで、mockは対象外。

## 7. 避けるべき承認パターン(このプロジェクト文脈)

- **ファイルごと・コマンドごとの承認**: L1に該当する限りollamaで自動承認する。
  今日の実運用の「main.js編集」「テスト実行」の個別エスカレーションはこれに該当した
- **技術名だけの承認要求**: 「apply_patch tests/test_agent_wrapper.py」ではなく
  「何がどう変わるか」を説明する(explain_operationの役割。判断材料の常設表示TODOと連動)
- **曖昧な一括許可**: 「必要な変更をすべて実行してよいですか」への自動yは禁止。
  judge_conversational_questionのESCALATE基準に「範囲が特定できない包括的な確認」を含める
- **重要な承認を軽微な承認に埋もれさせない**: L1の自動化はこのための手段でもある
  (承認回数が減れば、残った承認は本当に読むべきものになる)

## 8. codexのOSサンドボックスの扱い(2026-07-11 ユーザー決定)

`--agent codex` のOSサンドボックスは既定で `danger-full-access`(サンドボックスなし)とする。

- **承認ゲートはこの設定と無関係に常に有効**: approval-policy=untrustedにより全コマンド・
  全ファイル変更が実行前に elicitation→rules→ollama→人間 を通る。これが一次防壁
- サンドボックスは「承認をすり抜けた後の第二の壁」だが、Windowsでは読み取りすら
  誤ブロックする不安定さに加え、サンドボックス起因の失敗を昇格付きで再実行する
  承認要求がmcp経由でクライアントに届かない上流バグ(openai/codex#21982系統)があり、
  実運用で作業を複数回停止させた。「守らないのにコストだけ払う壁」と判断して既定オフ
- 失うもの(正直な記録): ollamaのL1自動承認や人間承認が誤った場合の被害半径が
  cwd内からユーザー権限全体に広がる。補償は壁ではなく判定の質
  (L1機械的事実・フェイルセーフESCALATE・監査1行ログ)で積む
- 信頼できないコードを扱うタスクでは `--codex-sandbox workspace-write` を指定する
- 上流バグが修正されたら既定を見直す(tasks/todo.md参照)
