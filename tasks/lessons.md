## 2026-07-08 AIエージェント・ラッパー プロトタイプ実装
- このリポジトリは `uv run pytest` を実行してもリポジトリルートが `sys.path` に入らず、`tests/` から `from <package>.core import ...` のようなimportが失敗する状態だった(既存の `test_filename_normalizer.py` も実は同じ理由で壊れていた)。`pyproject.toml` に `[tool.pytest.ini_options]` `pythonpath = ["."]` を追加して解決。パッケージ配下をimportするテストを書くときは、まず素の状態でpytestが通るか確認したほうがよい。
- Windows + Git Bash から `curl -F` / `curl -d` に日本語文字列をシェル引数として直接渡すと、文字化け(mojibake)してサーバー側に保存・送信されることがある(yadorigiへのingestで発生、ollamaへのプロンプト送信でも再現)。多バイト文字を含むペイロードは一時ファイルに書き出し、`curl --data-binary @file` や `curl -F field=<file` のようにファイル経由で渡すと安全。
- `wrapper.py` の `SharedState.approve_event` は単一の `threading.Event` なので、権限確認待ち(read loop thread)と定期チェックイン(checkin thread)が同時に `waiting_human` を要求すると、片方への承認(`approve()`)がその両方の待機を同時に解除してしまう競合状態がある。デフォルトの `checkin_interval_sec=600` では起きにくいが、検証用に間隔を数秒まで短縮すると容易に再現する。将来直すなら、pending要因ごとに別々の待機キューを持たせる設計に変更する必要がある。
- ollamaへの接続先(`http://localhost:11434`)自体は生きていても、コードに決め打ちしたモデル名が手元にpullされていなければ `/api/generate` は `404 {"error": "model '<name>' not found"}` を返す。これは接続不可とは別の失敗モードなので、モデル名をハードコードする前に `curl :11434/api/tags` で実際にpull済みのモデル一覧を確認してから決めるべき。


## 2026-07-08 AIエージェント・ラッパー 通知・LAN公開・ワンコマンド化
- ntfy.sh の JSON publish API (`POST https://ntfy.sh`, body に `topic`/`title`/`message`/`priority`) は `priority` を**整数(1〜5)でなければ受け付けず**、`"urgent"` のような文字列を渡すと `400 {"code":40024,"error":"invalid request: request body must be valid JSON"}` という紛らわしいエラーになる(文字列名はHTTPヘッダ方式でのみ有効)。実装前に実際にAPIへ最小構成のリクエストを投げて確認したことでこのバグを実装前に潰せた。
- Windows上のPythonコンソール既定コードページ(cp932)は `qrcode` パッケージの `print_ascii()` が使うUnicodeブロック文字(`█`等)を描画できず `UnicodeEncodeError` で丸ごとクラッシュする。`sys.stdout.reconfigure(encoding="utf-8")` を `main()` の先頭で呼ぶと解決し、副産物として引数ヘルプ等の日本語文字化けも同時に直る。同じパターンは `job_osint/main.py` に既にあった(`sys.stdout.reconfigure(encoding="utf-8")`)ので、Windows向けCLIで日本語やUnicode特殊文字を標準出力するときは最初から入れておくとよい。
- `uv tool install -e .` でプロジェクトをコンソールコマンド化するには、`[build-system]`(hatchling)・`[project.scripts]`・`[tool.hatch.build.targets.wheel] packages=[...]` が必要。ただしリポジトリ直下に無関係な多数のスクリプトがある場合、`packages` で対象パッケージを明示しないとhatchlingがビルド対象を特定できずに失敗する。
- `uv tool install -e .` でインストールした実行ファイルは、動作中のプロセスがロックを持っていると `--reinstall` が `os error 5 (アクセスが拒否されました)` で失敗する。バックグラウンドで起動したテストプロセスをちゃんと確認せずに再インストールすると壊れた状態(`No pyvenv.cfg file`)になることがあるので、`tasklist | grep` で実プロセスを確認してから `taskkill //F //PID` で確実に止め、それでも壊れたら `uv tool uninstall` してから入れ直すとよい。
- ntfy.shのトピック名はそれを知っている人なら誰でも購読できる「実質的な合言葉」なので、動作確認用にAIが生成したトピック名であっても、README.mdのようなgit管理下のファイルに実際の値をそのまま書き込んではいけない。生成コマンドと手順だけをドキュメント化し、実際の値はチャット上または環境変数など非トラッキングの場所に留める。


## 2026-07-08 AIエージェント・ラッパー インストール系操作の強制確認化
- ユーザーから「インストールをストップ要件にしてほしい」という要望があった際、最初はAI(Claude Code)自身がこのセッション中に行っているインストール操作(sfw uv add等)への指摘だと誤解した。実際は「agent_wrapperがラップしている側のエージェントが実行しようとするインストール系コマンド」を、削除系操作と同じくルールエンジンで強制的に人間確認へ格上げしてほしい、という要件だった。「〜をストップしてほしい」という発言は、直近の自分の行動(このセッションでのインストール)に結びつけて早合点せず、対象がどのレイヤー(このAI自身の作業か、ラップ対象のエージェントの挙動か)を指しているかを確認してから対応すべき。
- `rules.py` の `DESTRUCTIVE_PATTERNS` は行の内容全体に対して正規表現でマッチするため、`::REQUEST_PERMISSION::` マーカー付きの行であっても、マーカー処理より先に `check_destructive()` が呼ばれれば(`wrapper.py` の `_handle_line` の実装がそうなっている)、エージェントの自己申告(権限確認)よりも先に強制停止が優先される。この順序に依存する挙動を変えるときは、結合テストで実際にどちらが先に発火するかを確認する必要がある(npm installをdestructiveに追加した際、既存の結合テストの期待値(permission_escalated)が壊れて気づいた)。
- 新パターンを追加した副作用で、既存のテスト/デモ用データ(mock_agent.pyの唯一の`::REQUEST_PERMISSION::`行)が意図せず別の分岐に飲み込まれ、元々検証できていたはずの経路(ollama経由の一次判定)が無自覚にテスト対象外になっていた。ルールエンジンのパターンを追加・変更するときは、既存のテスト用サンプル行がどの分岐に落ちるか一つずつ再確認し、必要ならテスト専用の非破壊的サンプルを別途追加すること。


## 2026-07-08 AIエージェント・ラッパー コードレビュー指摘の修正
- `ruff check` は毎回実行していたが `ruff format` は一度もかけていなかった(check≠formatと認識していたつもりが実行を漏らしていた)。以後、pytest/ruff check/mypyのセットに `ruff format --check` も必ず含めること。
- 正規表現の「これで検知できるはず」は実際に `re.search()` で試すまで信用しないこと。`\bformat\s+[a-zA-Z]:\b` は一見もっともらしいが、コロンの後に単語文字が続かない限り末尾の`\b`が成立せず、現実的な入力(`format C:`, `format C: 実行`等)ではほぼ100%マッチしない。危険操作を検知する正規表現は、追加時に実際の入力例で `check_destructive()` を呼んで確認するテストを必ず一緒に書く。
- 「安全側に倒す」設計は、例外(接続失敗)だけでなく「応答はあったが期待した形式ではなかった」場合にも同じ方向に倒れているか確認すること。`judge_is_major_decision`は接続失敗時はTrue(安全側)なのに、モデルが"YES"という英単語を含まない形式で答えただけでFalse(見逃す側)になっており、フェイルセーフの対称性が崩れていた。`judge_permission`のような「明確にNOと言った場合だけFalse、それ以外はTrue」という対称的な判定に揃えると気づきやすい。
- ダッシュボードのようなUIから呼ばれる操作(approve/deny)は、「呼ばれた時点で本当にその操作が有効な状態か」をサーバー側で必ず再確認すること。待機中かどうかを見ずに常にstdinへ書き込む実装だと、二度押しや状態遷移後のクリックで書き込まれた入力が、後で発生する別の本物の確認要求に紛れ込んで無自覚に消費される。


## 2026-07-08 AIエージェント・ラッパー ヘッドレスモードの制約とSDK統合方針
- ユーザーの発言を早合点しないこと。「dangerously bypassは要らないでしょ、ollamaが許可を出したりするので」と明確に言われた直後に、別の発言(「今のは残していいんじゃない」)を「じゃあdangerouslyのままでいいってことか」と自分に都合よく解釈して実装を進めてしまい、後で「dangerouslyは使わないって話だったよね」と訂正された。相手の直近の明確な意思表示と矛盾するように見える発言が来たときは、勝手に前の発言を上書きせず、両立する解釈(この場合は「claude/codexの別ルーティングは維持していい」という別の論点への言及だった)を先に確認すべきだった。
- `claude -p`(ヘッドレスモード)は `--dangerously-skip-permissions` を外すと、権限確認が必要な場面でプレーンテキストの確認要求を出力するが、**stdinからの入力を待たずにそのままプロセスが終了する**(実機で確認: `jobs`/`tasklist`のいずれにもプロセスが残っていなかった)。「ラッパー側でstdinにy/nを書き込んで承認する」という設計は、ヘッドレスモード+権限確認有効の組み合わせでは原理的に成立しない。
- Claude Codeには権限確認を構造化JSON(`sdk_control_request`/`control_response`)でやり取りする`--input-format/--output-format stream-json`という仕組みが公式に存在するが、生のCLIフラグだけで自前実装するのは、プロンプトの初期送信をstdin経由のJSONで行う必要がある等の細かい作法があり、簡単に動かない(実機でハングを確認)。`--permission-prompt-tool`のような一部フラグは`--help`にも出てこず、ドキュメントとインストール済みバージョンの間にズレがある。この手のプロトコルを自前実装するのは、公式の`claude-agent-sdk`(Python, canUseToolコールバックあり)を使うことの再発明になるので避けるべき。
- `openai-codex`(Python SDK)はまだベータ版(0.1.0b3)で、承認コールバックの正確なAPIも未確認。claude側とcodex側で統合の確度が大きく違うことを認識し、無理に両方同時に進めようとしない。
- 大きな設計転換が必要と分かった時点で、コードを書き始める前にまず調査結果と移行計画をドキュメント化した(docs/agent_wrapper_sdk_integration_plan.md)。ユーザーからの「ドキュメントに詳細を書いて」という指示は、次回セッションが今回の文脈(何を試して何が分かったか)を再現なしに引き継げるようにという意図だったので、調査の経緯・具体的なAPIコード例・未解決の疑問まで含めて書くこと。


## 2026-07-08 AIエージェント・ラッパー SDK統合Phase1: can_use_tool単体の限界とPreToolUseフックの発見
- 「スクラッチじゃなくてsubscで作って」という短い指示は、(1)検証コードの置き場所をスクラッチパッドではなくリポジトリ内の永続的な場所にすること、(2)課金経路をAnthropic APIの従量課金ではなくサブスクリプションにすること、の2点を同時に指していた。曖昧な短い指示を早合点せず、AskUserQuestionで両方の論点を分けて確認したことで正しく認識合わせできた。
- `claude_agent_sdk` の `can_use_tool` コールバックは、**Claude自身が「確認が必要」と内部判断した呼び出しにしか発火しない**(GitHub Issue #912で仕様として確認)。Read/Bash両方で、単純な操作(ファイル読み取り、`echo`)は`can_use_tool`を経由せず0回のまま実行されてしまうことを実機で確認した。これは`rules.py`のように「Claude自身の判断より厳しく、正規表現で強制的に判定したい」という目的には`can_use_tool`単体では合わない、という重要な設計上の限界。
- 解決策は `PreToolUse` フック(`ClaudeAgentOptions(hooks={"PreToolUse": [HookMatcher(matcher="Bash", hooks=[...])]})`)。これはマッチした全てのツール呼び出しで**無条件に**発火し、戻り値の`hookSpecificOutput.permissionDecision`で`"allow"/"deny"/"ask"`を直接指定できる。`"ask"`を返すと`can_use_tool`に処理が渡る。`PreToolUse`フックで即denyする層(rules.py相当)と、`ask`経由で`can_use_tool`に判定を回す層(ollama_client.py相当)を組み合わせる3層構造を実機で検証し、期待通り動作することを確認した(agent_wrapper/sdk_prototype/probe.py)。
- 課金経路は`SystemMessage(subtype='init')`の`apiKeySource: 'none'`と`RateLimitEvent(rate_limit_type='five_hour')`から、サブスクリプション経由(APIキー従量課金ではない)であることを実機で確認できた。SDKが内部で`claude` CLIをサブプロセス起動する設計である以上、ドキュメント通りの挙動だったが、`total_cost_usd`のようなコスト情報がレスポンスに含まれていても、それは表示上の見積もりであり実際の請求はサブスク枠消費であることに注意(混同しやすい)。
- 検証中、Read工具の初回テストで一時ディレクトリ(`tempfile.TemporaryDirectory()`のデフォルト位置)がこのマシンの`~/.claude/settings.json`にある既存の許可ルール(`Read(//c/Users/perso/AppData/Local/Temp/**)`)に偶然一致し、`setting_sources=[]`(SDK隔離モード)を指定していても`can_use_tool`を経由せず自動承認された。SDKの隔離モードを使っていても、このマシン固有の既存設定が検証結果を汚染しうることを念頭に置き、検証用の一時ディレクトリ/コマンド文字列は既存の許可ルールと衝突しないものを選ぶこと。


## 2026-07-08 AIエージェント・ラッパー Phase2計画: rules.check_destructive一致は「即deny」ではなく「必ず人間確認」
- Phase2の設計を提示した際、`rules.check_destructive()`に一致したツール呼び出しを`PreToolUse`フックで**即denyする**という計画を立ててしまったが、これは誤りだった。ユーザーから「denyってなに？あなたの理解が間違ってない？」と指摘され、既存の`wrapper.py`の`_handle_line()`を見返すと、破壊的パターンに一致した場合の設計は「AIが自動で拒否する」のではなく「`state.set_waiting("destructive", reason)`で必ず人間の承認待ちにし、人間がy/nを判断する」というものだった。このプロジェクト全体の一貫した思想は「危険そうな操作でもAIが独断で拒否せず、最終判断は常に人間に委ねる」であり、Phase1のプロトタイプ(probe.py)で検証した「PreToolUseフックが即deny」というパターンは、あくまで technical feasibility(denyが実際に機能するか)の確認用であって、実運用の望ましい挙動そのものではなかった。
- 教訓: SDK統合のような大きな設計変更を行うとき、新しい技術要素(PreToolUseフックのpermissionDecision機構)に気を取られて、既存コード(`wrapper.py`)が体現している一貫した設計思想を読み落とし、実装しやすい形(即deny)に寄せてしまうことがある。新しいレイヤーを設計する際は、既存コードの対応箇所を先に読み直し、「これは何を模倣すべきものか」を明示的に確認してから計画を立てること。
- 修正後の設計: `PreToolUse`フックはBash/Write/Editに対して常に`"ask"`を返すだけ(判定ロジックを持たせない)。`can_use_tool`側で`rules.check_destructive()`相当の判定を行い、一致すれば(ollamaを経由せず)人間の承認待ちに直行、一致しなければ`ollama_client.judge_permission()`の一次判定を経てAllow/人間エスカレーションに分岐する。既存の`_handle_line()`と1対1で対応させる。


## 2026-07-09 AIエージェント・ラッパー 実機スモークテストで発見: CLAUDE.md混入とollama会話応答レイヤー
- `ClaudeRunner`の実機スモークテスト(`agent_wrapper/sdk_prototype/smoke_claude_runner.py`)を初めて実行したところ、Phase1の最初の`probe.py`実行と同じ現象(このマシンの`~/.claude/CLAUDE.md`が一時ディレクトリでのセッションにも混入し、Bashツールを実際に呼ぶ前にプレーンテキストで「y/nで確認してください」と尋ねて止まる)が再発した。**実装時に単体テスト(モックベース)を全て通していても、実機で実際にSDKを起動しなければ気づけないクラスの不具合がある**ことを再確認した。Phase2の実装中は一度も実機起動していなかったため、単体テストのグリーンだけでは「動く」ことの証明にならない。
- `setting_sources=["project"]`(ドキュメント上は「userレベルの設定を除外し、projectレベルのみ読み込む」はず)を指定しても、`~/.claude/CLAUDE.md`の混入を防げなかった。原因は未確定だが、`setting_sources`は主に`settings.json`(許可/拒否ルール・フック)の読み込み制御であり、ユーザーレベルの`CLAUDE.md`はこれとは別経路で常に読み込まれる可能性がある。ドキュメントの記載(`setting_sources`で制御できる)を鵜呑みにせず、実機で期待通りの挙動になっているかを都度確認する必要がある。
- ユーザーから「y/nであればollamaに答えさせればいい、回答を返すのもollamaの仕事だと思う」という提案があり、これに従って`query()`(一発投げっぱなし)から`ClaudeSDKClient`(対話継続可能)への切り替えを実施。`ollama_client.answer_conversational_question()`(会話文が確認質問かどうかを判定しつつ短い返答を1回のollama呼び出しで生成)を追加し、`ClaudeRunner._converse()`で最大5ターンまで自動応答するループを実装した。**重要な設計上の安全性**: この会話応答レイヤーは「進めてよいか」という相槌への一次対応に過ぎず、実際のツール実行(Bash/Write/Edit)の可否は引き続き独立して`PreToolUse`/`can_use_tool`側の`rules.check_destructive()`/`judge_permission()`が判定する。つまりollamaが会話で「y」と答えても、それだけでは危険な操作は実行されない(二重の安全網になっている)。
- 結果的に、CLAUDE.md混入という根本原因は未解決のまま(要調査)だが、会話応答レイヤーがそれを実用上吸収し、PreToolUse→can_use_tool→ollama自動承認→ツール実行→セッション正常終了、というエンドツーエンドの流れが実機で確認できた。根本原因を追わなくても実用上十分な多層防御になっている場合、無理に深追いしすぎず「解決した動作」と「未解決の原因」を分けて記録し、次のブロッカーになるまでは保留してよい。


## 2026-07-09 AIエージェント・ラッパー ollamaの「一次受付」は判定であって相槌ではない
- 会話応答レイヤー(`answer_conversational_question()`)を実装した直後、ユーザーから「ollamaは内容を把握してyと回答してるんだよね？適当に相槌ではいって答えられると困るよ、一次受付って言ったよね」と指摘された。実装を見返すと、このollama_client.pyのdocstring冒頭には元々「一次受付のローカルモデル(ollama)との連携」と明記されていたにもかかわらず、`answer_conversational_question()`は「質問かどうか」の二値判定しかしておらず、質問だと判定した時点で**内容を評価せず**一律で肯定的な返答を生成する作りになっていた。既存の`judge_permission()`は同じollama_client.py内で「破壊的でなく明らかに安全ならALLOW、少しでもリスクがあればESCALATE」という内容評価をしているのに、新しく追加した会話応答レイヤーだけがその一貫性を欠いていた。
